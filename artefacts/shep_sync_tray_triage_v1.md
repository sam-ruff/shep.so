## Diagnosis

**Observed:** The screenshot shows the footer notice `Cognition sync failed: Account sync timed out without download progress`. Its formatted reader has a large grey body area and a horizontal scrollbar. A still image cannot show whether the window had been hidden, when the notice first appeared, whether the message had rendered completely, or why the provider stopped making progress.

**Code-supported sync path:** `src/engine/account_sync.rs:175-216` watches provider download progress and returns that error after 480 seconds without progress. `src/engine/mail_sync.rs:320-404` wraps it with the account name, imposes a separate 600-second refresh bound and emits `MailSyncFinished(account_key, result)`. A timeout establishes a stalled check, not a proven lost network connection. The scheduler emits the same event for manual and background checks without an origin marker. `src/ui/mod.rs:1756-1773` immediately turns every error into the global footer notice and tracks only one `(account, notice_time)`; each later failure replaces it. Success for that account clears its current notice, while another account's success does not. There is no continuous-failure grace period or per-account failure record.

**Code-supported tray risk:** `src/ui/mod.rs:1177-1188` calls `reopen_after_failed_close` when the window is hidden, any required write exists, and a new error notice appeared. `src/ui/tray.rs:307-326` sees only the new notice timestamp, not its source. Thus an unrelated `MailSyncFinished` error while a required write is pending can satisfy `hidden_write_failed` and call `restore_main_window`, which opens or focuses a window (`src/ui/tray.rs:55-66,258-270`). A sync-only hidden process is protected by the existing `has_required_close_work` condition. The actual screenshot does not prove that this mixed-work path occurred. Preserve the existing deliberate reopen for failed required writes, including the native tray regression at `scripts/e2e.py:1597`.

**Separate reader observation:** The horizontal scrollbar is supported for wide HTML (`src/ui/html_reader/pan.rs:1-35`) and has a fictional wide-table native test (`scripts/e2e.py:2697`). The grey area might be authored spacing, clipped content or a renderer defect. The screenshot does not expose the original MIME/HTML or a second viewport, so it is not evidence that the timeout caused this layout. Track a separate fictional-source reproduction and inspect `html_view_current`, width, pan and visible pixels before changing rendering. Never commit or publish the private message or this screenshot.

## Implementation contract for the next stage

1. Give mail sync results a typed origin and account/attempt identity through the scheduler and UI. Do not infer connectivity from error strings. Treat background connectivity/check failures as delayed status; keep explicit Refresh and provider mutation errors promptly visible. Decide whether a manual Refresh during an existing background failure should show its own immediate error without resetting the background timer.
2. Track failure by account from the **first observed failed background result**, initially with a 30-second monotonic grace period. A repeated failure for the same continuously failing account must retain its original start. Successful recovery resets that account. A timer/tick publishes only an eligible, still-current account failure; dismissing a visible banner need not erase the underlying failure. Fence late results against attempt generations and committed account removal. A later healthy account must not clear or delay an older failing account. Multiple eligible accounts need stable, non-sensitive summary text.
3. Separate notice provenance from required-write recovery. Background sync errors must never trigger a tray-hidden window restore, including while a send, draft, attachment or other required write is pending. Preserve restoration when the **owned required write** fails and close recovery needs a visible editor or reason. Preserve explicit tray Open, activation, temporary saving fallback, missing-host behaviour and Quit semantics.
4. If the reader can be reproduced with fictional HTML, fix it as a separate renderer/layout issue. Compare the formatted and plain versions and inspect the actual frame before attributing it to sync. If reproduction fails, leave the reader diagnosis open rather than changing HTML sanitisation or width heuristics speculatively.
5. Update `docs/CLIENT_PARITY.md`, shared client scenarios and `TODO.md` for the desktop behaviour and any Flutter/browser gaps. The repository rule at `AGENTS.md:145` requires this when desktop failure/recovery behaviour changes. Browser refresh errors currently show immediately (`web/src/model.ts:1369-1420`, `web/src/ui.ts:3039-3057`); Flutter has a notice bar (`flutter/lib/ui/mail_action_banner.dart`). Their background sync contracts need review before declaring parity.

## Verification plan

- Deterministic Rust state tests using a controlled clock: error before/at 30 seconds, repeated failure, recovery and new failure, interleaved accounts, stale result, removed account, manual Refresh, dismissal and competing action error. Test a background timeout while a required write is pending and assert `tray.window` stays absent; separately prove the write's own failure reopens the intact recovery view.
- Exercise actual scheduler/result provenance with injected failure and held-progress fixtures; test cancellation and a post-removal reply without a live provider. Retain `src/engine/account_sync/tests.rs` progress/cache-drain contracts.
- Use `iced_test` for the visible/dismissed banner and explicit error controls where supported (`src/ui/simulator_tests/`); use the Shep native MCP harness for the Linux tray lifecycle, because headless widget tests do not prove native hide/focus. Extend `scripts/e2e.py` around the saved `test_tray_native_*` scenarios with a fictional held background failure overlapping a pending write. Assert hidden state before/after failure, no newly focused window, delayed banner after explicit Open, and required-write recovery. Review light and compact dark captures without personal data. Native fixture evidence is distinct from live provider and Windows/macOS execution.
- For the reader, compare the fictional wide-table and long-formatted fixtures in normal, compact and full-reader layouts; verify horizontal pan exposes expected text and screenshot pixels. Add a regression only for a reproduced defect.
- Run `cargo fmt --check`, relevant Rust tests, Clippy without suppressions, `cargo build --profile test-ui --features test-support`, selected native scenarios, and the browser/Flutter checks for any parity implementation. Preserve disabled client quality/release workflows and self-hosted runner policy.

## Principal assumptions and limits

1. Thirty seconds begins at the first **observed failed result** because no verified connection-loss signal is established here; the 480-second watchdog may already have elapsed before it appears.
2. `MailSyncFinished` currently lacks manual/background origin and immutable attempt identity, so a UI-only string filter would be insufficient.
3. The mixed required-write plus sync-failure tray path is established by code conditions but has not been reproduced in a native window in this stage.
4. The formatted-reader blank area has no demonstrated causal link to the timeout and no reproducible source HTML; its status remains uncertain.
5. Linux isolated fixtures can verify native tray mechanics, but actual provider behaviour and Windows/macOS tray execution remain separate checks.

No source files were changed and no tests were run in this analysis stage.
