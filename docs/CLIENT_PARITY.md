# Client parity

The root Rust + iced app remains the reference. Android/iOS live in `flutter/`; the desktop-style browser client lives separately in `web/`. `website/` promotes all clients. Development stays in review worktrees; the combined checkpoint is pushed to [`feat/mobile-web-clients`](https://github.com/sam-ruff/shep.so/tree/feat/mobile-web-clients). No main merge has occurred. The requested VPS installation awaits the supplied server and OAuth configuration.

**The new clients are not feature-complete.** Flutter production has a Rust bridge, SQLite cache/drafts, device credentials, mail setup and reviewed Outbox recovery. The Android integration suite and six Appium stages cover the implemented paths; full protocol-success/recovery coverage remains open. The separate browser connects to the Rust gateway, with account verification, an IndexedDB mail/draft cache and reserved SMTP sends; complete provider/recovery parity remains open. Preview builds acknowledge fictional state only. No personal account or credential is used by these tests.

Every desktop feature/default/provider change must update this matrix and the corresponding client scenario, or leave an explicit gap in the [active tracker](https://github.com/sam-ruff/shep.so/blob/main/TODO.md). [Agent instructions](https://github.com/sam-ruff/shep.so/blob/main/AGENTS.md) make this an ongoing requirement. `scripts/clients/check_parity.py --base REV` checks that desktop changes include a parity review; it does not certify feature equivalence.

## Browser transport and storage

A static browser app can be served to other devices over a network; that does not share a mailbox or authorize access to another device's secrets. Each browser has its own storage and provider session. The hosting server serves public promo assets and gates browser assets/API access through the Rust service. It has no persistent mail/password store. Authentication state is in memory; Google OAuth application credentials are deployment configuration, not mailbox credentials.

R74 now authorizes a Rust backend on the email VPS for beta verification and IMAP/POP3/SMTP. This supersedes static-only hosting and the optional local bridge. `backend/` implements Google login, an administrator allowlist and bounded mail endpoints using `shared/mail-core`. All app/API access is gated server-side. Mail endpoints remain disabled until an administrator configures exact hostname/port/IP pins; the browser adapter uses per-identity IndexedDB and tab-memory passwords. Exact owner identity, OAuth configuration and VPS target are pending. Passwords/mail must remain transient on the VPS, with client-side durable state, TLS, bounded queues, per-user isolation and safe SMTP retry semantics before live transport is enabled.

Preference storage contains appearance/layout/shortcuts only, scoped by a hash of the verified Google subject and OAuth client. Production mail/raw MIME, accounts, drafts and delivery records use the matching IndexedDB profile. Passwords stay in tab memory and reconnect is required after reload. The browser cache is not encrypted; secure remembered credentials, encrypted cache and provider OAuth remain open. Fixture mail/drafts/events stay in memory. Never put passwords or refresh tokens in localStorage. Production builds exclude the separate fictional preview entry. The Flutter web build is an automation surface for the mobile UI; it is not the separately requested hosted desktop client.

## Review and release

Use `flutter/test/preview_main.dart` only for preview builds, with the Android `preview` flavor (separate package). Production uses `flutter/lib/main.dart` and the `production` flavor. Browser production uses `web/index.html`; `preview.html` has a separate build output. All artifacts/logs belong under ignored `artifacts/`.

The disabled quality definition includes the client checks alongside Rust so the existing release trigger still waits for the whole quality workflow. Store signing, Apple distribution and all-client artifact publication remain a release prerequisite; the disabled release workflow refuses publication until a reviewed parity/release-readiness record permits it. The existing documentation deployment workflow is unchanged.

Saved host, native and browser scenarios are listed in the [shared scenario registry](https://github.com/sam-ruff/shep.so/blob/feat/mobile-web-clients/shared/client-scenarios.json) (see the [testing guide](CLIENT_TESTING.md)). The completion log records actual execution and shipping; no claim of complete HTML, Apple or final performance parity follows from these fixtures. Mobile notification/badge equivalents remain open.

Shared MIME selection now retains the last supported nonempty alternatives, related-root identity and separate CID scopes for mixed sections. Cache text/replies and file indicators use the same classification; a named inline image is not an attachment unless explicitly attached. Native Rust and WASM use shared fixtures. Flutter prepares the same confined document through two independent native rendering slots and keeps its system WebView mounted through controls and plain-text switching. The separate browser now prepares resource-confined HTML on an independent cancellable worker and renders it in a persistent opaque sandbox. Shared native/WASM preparation tests and saved browser controls cover CSS/tables, inline images, selection/Copy, Find across spans, quote visibility, plain-text choice, links, cancellation/retry and active-content isolation. Native Flutter integration and saved Android/browser controls now have evidence in the completion log; remote-image policy, large-layout bounds and Apple execution remain open. Incoming raw MIME passes an iterative nesting check before the pinned recursive parser. This does not remove the 25 MiB limit, provide streaming, or establish final performance. Mobile/browser selection and bulk-action parity remain active.

The containing website CSP includes the exact shared display-runtime hash; the frame adds a restrictive policy and `sandbox="allow-scripts"` without same-origin permission. Keep the gateway and web build from the same source revision. Missing/mismatched runtime permission produces a visible plain-text fallback and Retry. The owned runtime alone controls document indexing/highlights; mail scripts, forms, frames and automatic remote resources do not survive preparation. Converted inline images currently retain dimensions up to 2048×2048, with at most 32 MiB of aggregate decoded pixels. These bounds do not fulfill R23 streaming/large-mail work.

Flutter uses Android WebView and iOS WKWebView; iOS targets 14.0 for the shared WebP resources. A separate native semaphore bounds preparation without occupying provider or Find slots. The trusted display bridge rejects stale generations/layouts and coalesces commands. Platform-view and Find accessibility boundaries prevent the search input from intercepting document clicks. Native navigation, device content/file access and permission grants are denied; reviewed external links use the system handler. Flutter browser tests use the same opaque document and a JavaScript identity comparison for its cross-origin window. Remote-image exceptions/loading and Apple execution remain open.

Client Print uses complete cached MIME, independently of provider and formatted-reader capacity. It includes Subject/From/To/Cc/Date, full quoted history, attachment names and bounded inline WebP resources; Bcc and reply-thread headers are excluded. Native Android and the separate browser have actual printer/PDF evidence. UIKit's native adapter is implemented but still needs Apple compilation and execution. Opening or cancelling a dialog is never called successful printing. Remote-image policy, native shortcut parity, large-mail bounds, lifecycle/performance and other browser engines remain open.

Browser group ordering now retains the reviewed message through acknowledged moves and validated canonical aliases. Receipts keep the actual dispatch/Undo folder and UID separately from the frozen review. Persistent metadata and worker projections reject unrelated identity replacements. Saved browser controls cover an Archive group followed by Flag over all 125 messages, plus clearing stale History controls while another group loads; protocol/storage tests cover individual moves, UID recovery, alias rollback/flattening and cache-checkpoint recovery without repeating provider mutations.
